## 1. Purpose and success criteria

L6 puts a browser UI on the platform. It replaces the React SPA that was deleted
in `2c3cf59`, using the Laravel domain that L1–L5 built. It adds no domain rule:
every mutation already exists as a JSON endpoint with tests behind it. What is
new is presentation, the session-based HTML auth flow, and the small amount of
reading the UI needs that the JSON API never exposed.

Success looks like:

- A staff user signs in and can see the portfolio, open a patent, change its
  status, run the filing chain (`file → acknowledge → defect sheets →
  grant/reject`), upload/download/delete documents, and create users — from the
  browser, with no API client.
- An inventor signs in and can see their own patents, download a granted patent
  (single file or ZIP), request a pending one, and read their notifications.
- `GET /` sends each role to its home; guests reach `/login`; a wrong-role
  request gets a styled 403 page, never a JSON body.
- Light and dark themes built from `DESIGN.md`'s tokens. No mutation depends on
  JavaScript for its form: every create, edit and action is a real `<form>` or
  link. JS is limited to opening the confirmation dialogs, the mobile drawer and
  dismissing a toast.
- The JSON API is behaviourally unchanged: the 399-test baseline
  (1174 assertions) stays green and every L6 slice adds to it.
- The Dusk smoke suite runs in CI next to Pest; both jobs are green, and
  `vendor/bin/pint --dirty` is clean.

Two facts about the reference matter more than they look:

1. **`DESIGN.md` is not this product's design.** It is a token analysis of
   Mintlify's marketing and documentation site: atmospheric hero gradients, a
   3-column docs grid, pricing tiers, Inter + Geist Mono, mint accent, black
   pill buttons. Its *values* (colors, type scale, spacing, radii, elevation)
   are usable; its *layouts* describe a website this application is not, and it
   explicitly states that dark-mode token values were never published.
2. **The final SPA was thinner than the API behind it.** It had no generic
   status-change UI, so `PUBLISHED`, `EXAMINATION` and `MAINTENANCE` were
   unreachable through a browser. It never called the inventor granted-download
   or request-document endpoints (they existed in FastAPI/L4). Its users screen
   was read-only. Its documents tab sat behind the vault-unlock gate and
   countdown that ADR 0004 removed.

## 3. Decisions (2026-10-18)

1. **Blade, server-rendered, with no new UI framework.** Livewire is not used
   even though `livewire/livewire` 4.4.7 declares `illuminate/* ^13.0`: it would
   add a PHP dependency and a second testing paradigm (`Livewire::test`) to
   cover screens that are tables, forms and detail pages. Alpine is not used
   either: the only genuinely client-side behaviours are opening a `<dialog>`,
   the mobile drawer, and dismissing a toast, which is ~40 lines in the already
   wired `resources/js/app.js`. The one new dependency in L6 is `laravel/dusk`
   (dev-only, slice 4). Recorded in ADR 0006 because it diverges from the
   migration design's "Blade + Livewire 4" line.
2. **The URL is the state.** Filters, pagination, tab selection and deep links
   are query strings; mutations are `POST → redirect → flash`. No page fetches
   data with JavaScript. This keeps every behaviour assertable by a Pest HTTP
   test and matches the reference's own `?tab=`/`?focus=` URL state.
3. **The HTML layer lives beside the JSON, not instead of it.** Pages are added
   at `/login`, `/admin/*` and `/user/*`; the JSON keeps its existing root paths
   and therefore its contract and tests. One controller action serves both
   representations, negotiated with `expectsJson()`. Rejected: moving the API
   under `/api` (it would rewrite the L2–L5 contract for a cosmetic prefix) and
   duplicating a parallel set of HTML POST routes (two implementations of every
   mutation).
4. **Negotiation becomes explicit in three places**: `EnsureRole` (guest →
   redirect to login, wrong role → `abort(403)` for HTML), the
   `AuthenticationException` renderer (JSON only; let Laravel's redirect-to-login
   stand for HTML), and the 17 domain-exception renderers (HTML → back with a
   form error, JSON byte-identical to today).
5. **`DESIGN.md` supplies tokens, not layout.** Its colour, type, spacing,
   radius and elevation values are implemented once as Tailwind v4 theme
   variables; its marketing/documentation layouts are not ported; the dark
   palette it admits it never published is defined in §7.3.
6. **Screens = the SPA's final surface, minus the vault, plus three deliberate
   additions**: a generic status-change form (§8.2.3), inventor download and
   request-document (§8.3.3), and MD-only user creation (§8.2.4). Each closes a
   hole where an already-built, already-tested endpoint had no way in through a
   browser. The vault unlock modal and countdown are not built (ADR 0004).
7. **Notifications are read-only.** A `NotificationFeed` read module plus
   `GET /notifications` (newest first, capped at 100). No schema change, so no
   mark-as-read; the reference had none either.
8. **One spec, four slices**, each independently green: shell & auth → admin →
   inventor → Dusk + CI (§12). The slices are execution order, not separate
   specs.

`POST /auth/register`, `PATCH /applications/{id}`, `POST /applications/{id}/status`,

is created.

Route collision check: no page path overlaps a JSON path (`/applications`,
`/documents`, `/users`, `/analytics`, `/admin/filing` all stay JSON).

## 5. Auth and authorization

### 5.1 Login and logout

`GET /login` renders the form (guest only; an authenticated visitor is redirected
to their home). The form posts to the existing `POST /auth/login`, which gains
one branch:

```php
// LoginController::store — success
if (! $request->expectsJson()) {
    return redirect()->intended(HomeFor::path(Auth::user()));
}

return response()->json(Auth::user(), 200);
```

Failures negotiate too. The JSON statuses (403 non-institution, 429 throttled,
401 bad credentials) and bodies are unchanged; for HTML each failure returns
`back()` with an error under `email`, using the reference's wording:

| Case | JSON | HTML |
|---|---|---|
| non-institution email | 403 `{"message":"Institution email required"}` | back + "Enter a valid institution email address." |
| throttled | 429 + `Retry-After: 600` | back + "Too many attempts. Please wait a few minutes and try again." |
| bad credentials | 401 `{"message":"Invalid credentials"}` | back + "Incorrect email or password. Please try again." |

Each HTML failure returns `back()->withInput($request->only('email'))` with the
error under `email`, so the password is never reflashed into the session.

Logout posts to `POST /auth/logout`: JSON keeps `204`; HTML redirects to
`/login`. Both keep the audit row. The 429 status is deliberately not preserved
on the HTML path (a redirect cannot carry it); the message is.

### 5.2 Roles

- Guests hitting any `/admin/*` or `/user/*` page are redirected to `/login` by
  `auth`, and `redirect()->intended()` returns them to the page they wanted.
- `EnsureRole` gains negotiation: JSON requests keep the current
  `401 {"message":"Unauthenticated."}` / `403 {"message":"Forbidden."}`; HTML
  requests redirect guests to `login` and `abort(403)` for a wrong role.
- The portal (`/user/*`) is guarded by `role:user`, matching the reference and
  the nav. Its detail page resolves the record through the existing
  confidentiality rule rather than `findOrFail`:
  `ApplicationVisibility::visibleTo(Application::query(), $viewer)->find($id)`.
  A miss is a 404, not a 403, so the UI never confirms that someone else's id
  exists (CONTEXT.md invariant 6, unchanged).
- Nav items are derived from `Role::can()` — the same ability matrix the API
  enforces. No second role list in Blade.

### 5.3 CSRF and methods

Every form carries `@csrf`; `PATCH` and `DELETE` are expressed with
`@method('PATCH')` / `@method('DELETE')` on a `POST` form. Tests need no token
because `PreventRequestForgery` skips verification under `runningUnitTests()`.

## 6. Controller and error contract

The pattern for every action that gains an HTML caller:

```php
$result = $this->domain->do(...);              // unchanged domain call

if ($request->expectsJson()) {
    return response()->json($result);          // unchanged JSON contract
}

return redirect()                              // presentation only
    ->route('admin.patents.show', $result)
    ->with('status', 'Patent application created.');
```

| Form | Target | HTML result |
|---|---|---|
| Login / logout | `POST /auth/login`, `/auth/logout` | §5.1 |
| Create application | `POST /applications` | `admin.patents.show` + `status` |
| Edit title / technology area | `PATCH /applications/{id}` | back + `status` |
| Change status | `POST /applications/{id}/status` | back + `status` |
| Upload document | `POST /applications/{id}/documents` | back + `status` |
| Delete document | `DELETE /applications/{id}/documents/{docId}` | back + `status` |
| Filing steps (file, acknowledge, defect sheet, grant, reject) | `POST /admin/filing/{id}/*` | back + `status`; grant adds `warning` when no document exists (§8.2.3) |
| Create user | `POST /auth/register` | back + `status` |
| Request document | `POST /applications/{id}/request-document` | back + `status` |
| Theme | `POST /theme` | back (cookie set) |

**Domain failures on HTML requests** are rendered as form errors, not JSON
blobs. One closure in `bootstrap/app.php` replaces the 17 per-class JSON bodies:

```php
$domainError = function (Throwable $e, Request $request, int $status, array $extra = []) {
    if ($request->expectsJson() || $request->is('api/*')) {
        return response()->json(['message' => $e->getMessage()] + $extra, $status);
    }

    // Never reflash the password field; files are not flashable anyway.
    return back()->withErrors(['form' => $e->getMessage()])
        ->withInput($request->except('password'));
};
```

Each existing renderer keeps its class and status (`422`, `404`, `409`, `413`,
`429`, `403`) and passes the payload through the closure, so JSON responses stay
byte-identical. `abort(403)` from a controller keeps Laravel's HTML error
rendering. Validation failures already redirect back with field errors for
non-JSON requests — unchanged.

Flash keys: `status` (success), `warning` (grant without a document), and the
default `$errors` bag (field errors, plus `form` for domain errors).

## 7. The shell

### 7.1 Layout and navigation

`resources/views/layouts/app.blade.php` is the authenticated shell:
skip-to-content link, sidebar (brand, nav), top bar (page eyebrow + title, theme
toggle, email + role, Sign out form), the flash region, `<main>` and a footer
line ("University of Peradeniya · Technology Transfer Office"). The guest layout
is a centred card with the same brand block as the reference login page.

`App\Support\Navigation::for(User $user): array` returns the items, each
`['label' => ..., 'route' => ..., 'active' => 'admin.patents.*']`. The nav is a
function of the same abilities the routes enforce, so the two cannot drift:

| Role (ability) | Items |
|---|---|
| `md` (`MANAGE_USERS`) | Overview (`admin.dashboard`), Patents (`admin.patents.index`), Users (`admin.users.index`) |
| `director` (`DOCKET`) | Overview (`admin.dashboard`), Patents (`admin.patents.index`) |
| `user` (neither) | Overview (`user.overview`), My Patents (`user.patents.index`), Notifications (`user.notifications.index`) |

The portal routes are `role:user`, mirroring the reference (`/user` was the
inventor area; staff were sent to `/admin`), so the nav and the route guards
agree in both directions. `App\Support\HomeFor::path(User): string` returns
`/admin` or `/user` and is used by `/`, post-login `intended()` and the 404
fallback.

Mobile: the sidebar is a drawer that toggles a class on `<html>` (or `.layout`)
with a backdrop; it is closed by default and is not persisted. Collapsing to
icons (the reference's 64px rail) is not built — the drawer covers the need
(YAGNI).

elevation (hairline borders; level-1 shadow on hover-elevated rows; level-2 for
modals), and the component recipes for primary (black pill; white pill on dark),
accent (mint), secondary (outline), ghost and danger buttons.

### 7.3 Dark mode (the gap `DESIGN.md` leaves)

`DESIGN.md` states no dark palette was published. We define the minimum needed
to keep the token names identical in both themes, deriving from the dark values
it *does* publish (`canvas-dark`, `hairline-dark`, `on-dark`, `on-dark-muted`):

| Token | Light | Dark |
|---|---|---|
| `canvas` | `#ffffff` | `#0a0a0a` |
| `surface` | `#f7f7f7` | `#141414` |
| `surface-soft` | `#fafafa` | `#1a1a1a` |
| `hairline` | `#e5e5e5` | `#1f1f1f` |
| `hairline-soft` | `#ededed` | `#262626` |
| `ink` | `#0a0a0a` | `#f5f5f5` |
| `charcoal` | `#1c1c1e` | `#ededec` |
| `slate` | `#3a3a3c` | `#d4d4d6` |
| `steel` | `#5a5a5c` | `#b3b3b3` |
| `muted` | `#a8a8aa` | `#7a7a7c` |
| `brand-green` | `#00d4a4` | `#00d4a4` (unchanged; on dark it is an accent on `canvas`) |
| `brand-error` | `#d45656` | `#f08a8a` (lightened for contrast on dark) |
| `brand-warn` | `#c37d0d` | `#e0a33a` |

Implementation: the `<html>` element gets `class="dark"` when the `blitto-theme`
cookie is `dark`, or — with no cookie — when a five-line inline script matches
`prefers-color-scheme: dark` (before first paint, so there is no flash). The
toggle is a header form posting the opposite theme to `POST /theme` (a hidden
`theme` field plus `@csrf`), which sets a one-year `SameSite=Lax` cookie and
redirects back. No JavaScript is required, the request is CSRF-protected, and
the choice survives a full page reload; it is per-browser, not per-user (no
schema change).

`resources/js/app.js` holds the whole client-side surface: open/close `<dialog>`
(including `showModal()` and focus return), toggle the drawer, dismiss a toast.
No build-time framework, no CDN. With JS unavailable the confirmation dialogs
simply cannot be opened, so an irreversible action is never submitted by
accident — and no other screen depends on it.

## 8. Screens

Each screen states data source, content, empty state and actions. All listings
are server-rendered from the existing domain read methods; no page calls the
JSON API over HTTP (same process, and it keeps the UI independent of the API
contract).

### 8.1 Slice 1 — shell and auth

- **`/login`** — email, password, submit; errors from §5.1; when already
  authenticated redirect to the home. Copy from the reference: "Welcome back",
  "Sign in to access your docket", "University of Peradeniya · Technology
  Transfer Office".
- **`/`** — redirect to `HomeFor::path($user)`, or `/login`.
- **Error pages** — `errors/403`, `errors/404`, `errors/419`, `errors/500` inside
  the shell (guest layout when unauthenticated), each with a "Go to dashboard"
  link. Laravel picks these up automatically.
- **Shell** — layout, nav, flash/toast region, theme toggle, sign-out form.
- **`resources/views/welcome.blade.php` is deleted.** `/` no longer renders a
  view, which is why `ExampleTest` changes (§10).

### 8.2 Slice 2 — staff

#### 8.2.1 `/admin` (director, md)

Data: `PortfolioAnalytics::portfolioSummary()`, `ApplicationIntakeService::listVisibleTo()`
(latest 5), `DocumentService::missingGrantedDocuments()`; for `md` only,
`UserDirectory::all()` counts/latest 5.

Content: stat cards **Total patents**, **Filed**, **Granted** (from

`deadlineReport()` — the L5 module already computes it; the card is
non-interactive, because the docketing screen is out of scope, §13), plus
**Users** / **Inventors** cards for `md` only. The patents cards link to the
patents list filtered by status. Below: Recent applications (title,
reference, status badge) with "View all"; Missing documents (granted patents
with no document) with a link to each detail — the L4 worklist finally gets a

#### 8.2.2 `/admin/patents` (director, md)

Data: `listVisibleTo($user)` for staff (all applications), filtered and
paginated by `App\Http\Presenters\PatentTable` (a presentation-only class, so
the controller stays a three-liner):

- `?q=` — case-insensitive match on title, inventor name/email, technology area,
  application number.
- `?status=` — one `ApplicationStatus` value or `all`.
- `?page=` — 15 rows per page via `LengthAwarePaginator` on the filtered
  collection, newest first (the domain orders oldest first for the API; the UI
  reverses for display).
- `?sort=` is **not** built (the reference had none).

Columns: Title, Reference (`application_number` or the first 8 chars of the
id), Status badge, Inventors (first name + "+N more"), Technology area, Updated.
Row links to the detail. Header: "Patents", "Manage the patent portfolio and its
documents", **New patent** link to `admin.patents.create`, result count ("N of M
patents"). Empty state: "No patents yet." with the New patent action; and a
separate "no matches" state when filters exclude everything, with a
clear-filters link.

**New patent is its own page** (`GET /admin/patents/create`), not a modal: it
has a repeatable inventor group and must work without JavaScript. Fields: title,
technology area, one or more inventors (name + institution email, "Add inventor"
— the second row is revealed by a `<details>`/CSS disclosure or simply rendered
as two blank rows). It posts to `POST /applications` and, on success, redirects to
the new patent's detail page. Server-side validation errors come back inline (the
existing `createRules` apply). `POST /applications` keeps its JSON contract for
API clients.

#### 8.2.3 `/admin/patents/{applicationId}` (director, md)

Data: the application, `ApplicationIntakeService::history()`, `DocumentService::listFor()`,
`FilingWorkflowService::filingRecord()`, `defectSheets()`, `FilingWorkflowService::grantWarning()`.

Sections:

1. **Header** — title, status badge, reference, technology area, created/updated,
   inventors.
2. **Edit technology area** (and title) — inline form posting `PATCH
   /applications/{id}`.
3. **Status change** — form with `new_status` (all `ApplicationStatus` cases) and
   a required `reason`, posting to `POST /applications/{id}/status`. This is a
   deliberate addition (§3.6): without it the three statuses that have no filing
   step are unreachable.
4. **Filing** — one panel showing the current filing record (filed date, NIPO
   acknowledgement, patent number) and the actions it makes plausible: no record
   → **File**; record without `nipo_acknowledged_at` → **Acknowledge**;
   acknowledged → **Add defect sheet** (`sheet_number` 1–3 + description),
   **Grant** (`patent_number`) and **Reject**.
   This grouping is a presentation heuristic read from `filingRecord()`, not a
   second transition table: `FilingWorkflowService` exposes no predicates
   (`LifecycleService::assertAllowed` is the rule, and it is not a UI API), so
   nothing is duplicated in Blade. The domain stays the authority — an action
   attempted in the wrong state comes back as a 422 form error (§6, §10).
   Grant and Reject open a confirm `<dialog>`; the reference's irreversibility
   checkbox is kept on grant as a client-side guard only. When the application
   is granted without a document, `grantWarning()` is shown before granting and
   the response's `warning` is flashed afterwards.
   Grant is also reachable through the generic status form (item 3); the two
   paths are deliberately worded differently by L5 ("Patent Received" from the
   filing chain, "GRANTED — download ready" from the status route) and L6 leaves
   that alone.
5. **Status history** — timeline (old → new, changed by, reason, time), newest
   first on screen.
6. **Documents** — table (filename, size, uploaded by, date) with Download and
   Delete (confirm dialog) actions, and an upload form (file input + submit)
   posting to `POST /applications/{id}/documents`. Empty state: "No documents
   uploaded yet."
   **Upload stays available after filing** — `DocumentService::store()` has no
   filing guard; CONTEXT.md invariant 3 is that only *new* documents may be
   added once filed. **Delete is the action the rule blocks**
   (`DocumentImmutability::assertModifiable()`): when the application has a
   filing record with a `filed_date`, the panel hides Delete and states why,
   instead of offering a button that always 409s.

## 9. Backend additions

Small, read-only, and tested like everything else.

```php
namespace App\Domain\Notification;

final class NotificationFeed
{
    /** @return Collection<int, Notification> newest first, at most 100 */
    public function forUser(User $user): Collection;

    public function countFor(User $user): int;
}
```

- `forUser()` — `recipient_email = $user->email`, `orderByDesc('sent_at')`,
  `orderByDesc('id')`, `limit(100)`. The cap bounds the payload; the reference
  had none and no paging.
- `countFor()` — used by the inventor overview card. There is deliberately no
  nav badge: a count that cannot distinguish read from unread would be noise,
  and the reference had none.
- `App\Http\Controllers\NotificationController@index` (`GET /notifications`,
  `auth`) returns `response()->json($feed->forUser($request->user()))` — each row
  is the model's own fields (`id`, `recipient_email`, `subject`, `body`, `kind`,
  `sent_at`), restoring the reference's `api.js` surface. The Blade page calls
  the feed directly, not this endpoint.
- `GrantedPatentService::alreadyRequested()` is promoted from private to
  `public function hasOpenRequest(Application $application, User $viewer): bool`
  (same audit-based check, used by the write path and now readable by the portal
  detail page). This is the only change to an existing domain class in L6.
- `App\Support\Navigation` and `App\Support\HomeFor` (§7.1) — presentation
  helpers, unit-tested through the rendered pages.

No schema change, no migration, no new domain rule, no new mail, no change to
`NotificationService`.

## 10. Testing strategy

Everything is Pest, `it('...', function () {...})`, `RefreshDatabase`, one test
at a time (TDD), through public interfaces (HTTP + rendered HTML). `tests/Pest.php`
gains `$this->withoutVite()` for Feature tests so `@vite` does not need a built
manifest.

| Area | Cases |
|---|---|
| Routing / auth | `/` redirects md/director → `/admin`, user → `/user`, guest → `/login`; each page redirects a guest to `login` with `intended`; wrong role → 403 (including director/md on `/user/*`); md-only users page; authenticated visitor on `/login` bounces through `home`; the create page is not shadowed by the detail route; `ExampleTest` is updated for the redirect |
| Negotiation | an existing JSON request keeps its exact body/status for each negotiated action (a representative set: login 401/403/429, status 422, upload 413, duplicate email 409); HTML failure → `back()` + `assertSessionHasErrors` + `withInput` |
| Login | success → redirect + authenticated + audit row; each failure message; throttle message; intended redirect after a guarded page |
| Admin pages | dashboard counts and missing-documents list; patents table columns, reference fallback, filters (`q`, `status`), page 2 of 15, result count; detail renders history/documents/filing state; users list and search; empty states |
| Admin forms | create application (from the create page) → redirect to detail + flash; edit technology area; status change (legal) → flash, (illegal) → form error and no status change; each filing step → flash, and a step attempted in the wrong state → form error (the grouping heuristic is not a guard); grant without document → warning flash and `grant_without_document` notification (already asserted by the domain suite); upload, list and delete a document; uploading after filing still succeeds; deleting an immutable document → form error and the Delete control is absent; user creation (md) → flash, director → 403 |
| Inventor pages | overview counts; patents list scoped to the viewer (another inventor's patent is 404); detail shows timeline; granted-with-document has the download link; granted-without-document has the request form and no download link; the request form is absent while an open request exists (`hasOpenRequest`, §9); request → flash, duplicate request → 409 flash; notifications newest-first and scoped to the viewer; empty states |
| Notification API | guest 401; returns only the viewer's rows; ordering; the 100-row cap; the exact JSON shape — an array of objects with `id`, `recipient_email`, `subject`, `body`, `kind`, `sent_at` and nothing else |
| Theme | no cookie → renders without `dark`; `blitto-theme=dark` cookie → `class="dark"`; `POST /theme` with `theme=dark` sets the cookie and redirects back; `theme=light` switches it back; any other value is rejected |
| Safety | a title containing `<script>` renders escaped (Blade defaults). CSRF itself is the framework's job and is skipped in tests (`PreventRequestForgery::runningUnitTests()`), so no test asserts a 419 |

The 399-test baseline is an acceptance criterion for every slice: no existing
test may be deleted or weakened; only `ExampleTest` changes, because `/` stops
being a 200.

## 11. CI

A second job, `backend-dusk`, runs the browser smoke suite. It is a separate job
so a flaky browser cannot mask a Pest failure and so the Pest job keeps its
current cost and stays asset-free (`withoutVite()` means Pest never needs a
Vite manifest).

```yaml
backend-dusk:
  name: backend-dusk (Dusk)
  runs-on: ubuntu-latest
  defaults: { run: { working-directory: backend } }
  env:
    # Same trap as #76: composer's post-autoload package:discover boots the app
    # before .env exists, so the environment must be declared up front.
    APP_ENV: local
    APP_URL: http://127.0.0.1:8000
    DB_CONNECTION: sqlite
    DB_DATABASE: ${{ github.workspace }}/backend/database/dusk.sqlite
    SESSION_DRIVER: file      # the browser and the app server are separate processes
    CACHE_STORE: array
    MAIL_MAILER: array
    BLITTODB_MAIL_CHANNEL: array
  steps:
    - uses: actions/checkout@v7
    - uses: shivammathur/setup-php@v2   # 8.3, sqlite/pdo, coverage none
    - run: composer install --no-interaction --prefer-dist --no-progress
    - run: cp .env.example .env && php artisan key:generate
    - run: cp .env .env.dusk.local       # Dusk prefers this file; job env still wins
    - run: touch database/dusk.sqlite && php artisan migrate:fresh --seed --force
    - run: npm install --no-audit --no-fund && npm run build   # no package-lock.json exists
    - run: php artisan dusk:chrome-driver --detect
    - run: php artisan dusk
    - uses: actions/upload-artifact@v4
      if: failure()
      with: { name: dusk-screenshots, path: backend/tests/Browser/screenshots }
```

`--seed` runs the L5 demo seeder (allowed in `local`), which gives the smoke
suite known accounts: `md@pdn.ac.lk` / `mdpw-123` (staff, 3 applications) and
`user-a@pdn.ac.lk` / `userapw-123` (2 applications, 1 notification, one GRANTED
patent with no document).

`phpunit.dusk.xml` is committed (Dusk's `dusk:install` generates it) with the
local defaults: `APP_ENV=local`, `APP_URL`, file-backed sqlite, `SESSION_DRIVER=file`,
`CACHE_STORE=array`, `MAIL_MAILER=array`, `BLITTODB_MAIL_CHANNEL=array`.
`.env.dusk.local` is **not** committed; a developer creates it by copying `.env`
and pointing `DB_DATABASE` at `database/dusk.sqlite`.

Smoke cases (five, thin by design — the behaviour is already covered by Pest):

1. Guest visiting `/admin` lands on `/login` and sees the form.
2. MD logs in → dashboard shows the three seeded patents and the Users nav item;
   sign out returns to `/login`.
3. Patents → open "Solar Desalination Membrane" → submit a legal status change →
   the new status badge and the success toast are visible.
4. Theme toggle → `<html>` has `dark` and it survives a reload (cookie).
5. Inventor logs in → `/user/notifications` shows the seeded notification;
   `/user/patents` shows their two patents and no one else's.

Artifacts: `tests/Browser/screenshots` on failure (Dusk's default) are uploaded
with `actions/upload-artifact` when the job fails. `phpunit.dusk.xml` is
committed (Dusk's install generates it); `.env.dusk.local` is not — the job's
`env:` block is the only environment the browser run gets.

## 14. Risks and open points

- **`DESIGN.md` is a marketing/documentation system.** Using its tokens on a
  data-dense internal tool is a deliberate interpretation of "DESIGN.md-faithful"
  (§3.5). The mint accent is confined to primary actions and active states, as
  its own rules demand; the hero gradients and docs grid are not used. If the
  result reads as "Mintlify docs site with tables", the fix is layout, not
  tokens.
- **The dark palette is ours** (§7.3) because the authority file leaves it
  blank. Contrast is checked by hand on the token pairs used (ink/canvas,
  ink/surface, on-dark/canvas, error/canvas); there is no automated contrast
  gate.
- **Negotiation touches shipped code.** `EnsureRole`, `AuthenticationException`
  and 19 renderers change. The mitigation is the JSON-contract tests already in
  the suite: every one of them must stay green untouched, and the HTML branches
  are additive.
- **The login page loses `429` on the HTML path** (a redirect cannot carry it).
  The message keeps the information; the JSON path keeps the status.
- **The `/theme` toggle is a navigation** (a form post, then a redirect), so it
  reloads the page and resets scroll. Acceptable for an internal tool; a
  JS-only alternative would trade testability and CSRF safety for smoothness.
- **Dusk is the first browser dependency in CI.** Chrome is present on
  `ubuntu-latest`; `dusk:chrome-driver --detect` pins the driver at runtime. If
  the job proves flaky it is scoped to five smokes and does not gate the Pest
  job's signal.
- **The reference snapshot is thin** (3 applications, 1 notification for the
  inventor, 0 filing records), so the demo UI shows sparse tables. That is the
  L5 seeder's known limitation, not an L6 defect; the Dusk smokes and Page tests
  create their own fixtures where they need more.
- **`POST /auth/register` keeps its existing self-registration rule**: any
  authenticated user may create a `user` account, and only `md` may create
  `director`/`md`. The create-user form is on the `md`-only page, but the
  endpoint's rule is unchanged by L6. Tightening it would be a domain change and
  belongs in its own issue.
